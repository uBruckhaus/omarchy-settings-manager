Review of `task/a-theme` ([theme_core.py](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py), [pages_theme.py](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py), [tests/test_theme_core.py](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/tests/test_theme_core.py), `translations/*/pages_theme.json`, [README.md](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/README.md), [docs/reports/a-theme.md](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/docs/reports/a-theme.md)).

### Findings

1. **High — [theme_core.py:209-213](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L209-L213) — `_clean_jpeg` stops at the first `SOS` (`0xDA`) and passes trailing segments untouched, bypassing EXIF/metadata stripping**
   - **Failure scenario:** `_clean_jpeg` appends `data[pos:]` and returns immediately on the first `0xDA` marker without walking to `EOI` (`0xD9`). Any `APP1` (EXIF/XMP), `APP2` (ICC), `APP13`, or `COM` segment placed after the first scan (between scans in a progressive JPEG, or right before `0xFFD9` in a baseline JPEG) passes `safe_image()` unstripped. Verified live against this machine's `GdkPixbuf 2.44.8` / `glycin`: inserting an `APP1` EXIF `Orientation=6` segment after `SOS` before `EOI` in both baseline and progressive JPEGs survived `safe_image()` and was parsed in-process by `glycin` (`pixbuf.get_option("orientation") == "6"`), defeating the crash/abort protection `safe_image()` exists to provide.
   - **Suggested fix:** After `0xDA`, scan through the entropy-coded data (skipping byte-stuffed `0xFF 0x00` and restart markers `0xFF 0xD0..0xD7`) until the next marker, keep stripping metadata (or allowlist only image/framing markers) across subsequent scans until `0xD9` (`EOI`), and reject if `EOI` is not reached within `MAX_IMAGE_WALK`.

2. **High — [theme_core.py:526](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L526) (and [460-461](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L460-L461)) — `apply_theme` invokes `["omarchy", "theme", "set", slug]`, which collides with `/usr/bin/omarchy-theme-set-*` subcommands on Omarchy 4.5**
   - **Failure scenario:** `/usr/share/omarchy/bin/omarchy` (`resolve_direct_route`, lines 442–465) performs longest-prefix matching against `omarchy-<a1>-<a2>-...`. Verified live on this system (`omarchy theme set gnome --help` → `omarchy-theme-set-gnome`, `omarchy theme set templates --help` → `omarchy-theme-set-templates`): 19 valid slugs (`browser`, `browser-policy`, `claude`, `fcitx5`, `foot`, `glass`, `gnome`, `herdr-machines`, `hermes`, `hunk`, `keyboard`, `keyboard-asus-rog`, `keyboard-f16`, `obsidian`, `pi`, `t3code`, `templates`, `tmux`, `vscode`) match `/usr/bin/omarchy-theme-set-*`. If a user installs or creates a theme with any of those folder names (e.g. `glass`, `gnome`, `obsidian`), clicking **Apply theme** executes that unrelated hook binary with no arguments instead of applying the theme.
   - **Suggested fix:** Run `["omarchy-theme-set", slug]` directly and check `shutil.which("omarchy-theme-set")` in `can_apply()` (matching how `plugins_core.py` invokes `omarchy-plugin-*` directly).

3. **Medium — [pages_theme.py:210-213](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L210-L213) and [pages_theme.py:270-275](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L270-L275) — `RatioBin.do_dispose` and `SideBySide.do_dispose` do not chain up to `Gtk.Widget.do_dispose`**
   - **Failure scenario:** PyGObject does not automatically chain up `do_dispose` (verified live on a `GObject.Object` subclass: overriding `do_dispose` without `super().do_dispose()` completely skips the parent class's `dispose` vfunc). Every time `ThemePages.refresh()` rebuilds the grid, all 31–40 `RatioBin` instances (and `SideBySide` on teardown) are disposed without `gtk_widget_dispose()` running, leaking internal GTK4 widget state/CSS nodes/controllers and risking GTK finalize warnings.
   - **Suggested fix:** Call `Gtk.Widget.do_dispose(self)` (or `super().do_dispose()`) at the end of both `RatioBin.do_dispose` and `SideBySide.do_dispose`.

4. **Medium — [theme_core.py:55](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L55), [theme_core.py:161-180](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L161-L180), and [pages_theme.py:54-61](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L54-L61) — 16-bit PNGs within `MAX_IMAGE_PIXELS` cause ~766 MiB in-process RSS spikes (3× the ~256 MiB assumption), and extreme aspect ratios bypass downscaling**
   - **Failure scenario:** `gdk-pixbuf 2.44` / `glycin` decodes the full-resolution frame before `size-prepared` scaling takes effect, and `_clean_png` ignores `IHDR` `bit_depth`. Verified live in an isolated process: a 500 KiB 8000×8000 16-bit RGBA PNG passes `safe_image()` and spikes in-process RSS from 30.4 MiB to **765.8 MiB** (512 MiB 16-bit buffer + 256 MiB 8-bit conversion) even with `ld.set_size(320, 320)`. Additionally, `scale = min(1.0, max(size[0] / width, size[1] / height))` (`pages_theme.py:54`) keeps `scale = 1.0` for extreme panoramas such as 16384×540, storing ~35 MiB RGBA `Gdk.MemoryTexture`s in the 160-entry LRU cache.
   - **Suggested fix:** Require `IHDR` `length == 13` in `_clean_png` and account for 16-bit depth (`bit_depth == 16`) with a tighter pixel cap (or reject 16-bit PNGs above ~16 MP). In `_decode`, also cap the scaled output's longest side / total pixels so extreme aspect ratios cannot pin tens of MiB per cached texture.

5. **Medium — [theme_core.py:367-373](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L367-L373) and [theme_core.py:281-289](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L281-L289) vs [theme_core.py:112](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L112) — Symlink handling mismatch between listing/cache-keying (`os.stat`) and reading (`O_NOFOLLOW`)**
   - **Failure scenario:** `_usable_image()` and `image_key()` use `os.stat()` (following symlinks), whereas `read_bytes()` opens with `os.O_NOFOLLOW`. If a theme contains a symlinked `preview.png` or `backgrounds/1.png` pointing to another image inside the trusted theme/background roots, `list_themes()` advertises it as a valid preview/wallpaper and `image_key()` generates a cache key, but `load_image()` always fails with `ELOOP`. Cards stay stuck on the swatch fallback, the big preview counts unviewable wallpapers in `1 / N`, and clicking `‹ ›` onto such a wallpaper advances the counter while leaving the previous image frozen.
   - **Suggested fix:** Use `os.lstat()` in both `_usable_image()` and `image_key()` so symlinked image files are consistently refused at discovery time (matching Rule 4 and `O_NOFOLLOW`).

6. **Medium — [pages_theme.py:773-784](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L773-L784) — Refreshing the page leaves `big_sources` and the big swatch fallback stale when the same theme remains selected**
   - **Failure scenario:** On **Refresh** (Ctrl+R / F5 / button), `_render()` calls `_ensure_selection(prefer=self.selected)` → `select(slug)` → `_show_big(slug)`. Because `slug == self.big_slug` and `self.big_swatch_holder.get_first_child() is not None`, line 773 skips rebuilding `self.big_sources` and `self.big_swatch_holder`. If wallpapers were added/removed or `colors.toml` was edited for the selected theme, `_update_big()` shows the new wallpaper count text while the picture's `‹ ›` buttons and `1 / N` counter remain stuck on the stale list (referencing deleted paths and missing new ones).
   - **Suggested fix:** Reset `self.big_slug = ""` (and cancel `self.auto_timer`) in `_render()` before calling `_ensure_selection()`.

7. **Medium — [pages_theme.py:924-926](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L924-L926) — `_refresh_current()` has no stale-answer guard**
   - **Failure scenario:** Unlike `load()`, `_refresh_current()` uses no generation counter and does not check `self.applying` when its callback lands. If two `_refresh_current()` calls overlap (rapid external switches, or an external monitor callback overlapping with `apply()` finishing, especially if one hits the `omarchy theme current` fallback), an older slow response can overwrite `self.data["current"]` and move the **In use** mark back to a stale theme.
   - **Suggested fix:** Maintain a monotonic `self._current_gen` incremented in `_refresh_current()` and `_render()`, and drop callbacks where `gen != self._current_gen` or `self.applying` is active.

8. **Low — [pages_theme.py:390-427](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L390-L427) — `ThemeCard._got_wall` can flip a card to its wallpaper after the pointer already left**
   - **Failure scenario:** If `flip_timer` fires and starts an async decode for `self.wall_path` via `_flip()`, and the pointer leaves before decoding completes, `on_leave()` cannot cancel the in-flight decode. When `_got_wall()` later delivers the texture, it switches `self.stack` from `"preview"` to `"wall"` while unhovered, leaving the card stuck showing its wallpaper.
   - **Suggested fix:** Track `self.hovered = True/False` in `on_enter()`/`on_leave()` and ignore `_got_wall()` when `not self.hovered`.

9. **Low — [pages_theme.py:619-634](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L619-L634), [666-672](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L666-L672), [730-735](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L730-L735) — `self.auto_timer` is not cancelled when hiding the big preview**
   - **Failure scenario:** When switching to an empty filter (e.g. Light while all light themes are hidden) or hitting an error/empty theme list within 2 s of selecting a theme, `self.big_bin` is hidden without calling `self._cancel_auto()` or clearing `self.big_sources`. When the timer fires, `_auto_step()` steps through the stale `big_sources` and triggers an unnecessary `BIG_SIZE` decode.
   - **Suggested fix:** Call `self._cancel_auto()` and clear `self.big_sources = []` in `_drop_cards()` and whenever hiding `self.big_bin`.

10. **Low — [theme_core.py:236-245](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L236-L245) & [pages_theme.py:72](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/pages_theme.py#L72) — `_clean_webp` skips `VP8 `/`VP8L` dimension checks when `VP8X` is present, and `_decode` misses `width == 1` mismatches**
    - **Failure scenario:** In `_clean_webp`, `elif kind == b"VP8 " and size is None` / `VP8L` skips parsing the bitstream dimensions whenever `VP8X` already set `size` (verified live: `VP8X(10x10)` + `VP8L(12000x12000)` passes `safe_image()` as `(10, 10)`, though `glycin`'s WebP loader rejects `Inconsistent image sizes` before decoding). In `pages_theme.py:72`, `pixbuf.get_width() <= 1 < width` fails to reject a size-prepared mismatch when the checked header had `width == 1` and `height > 1`.
    - **Suggested fix:** Always parse `VP8 `/`VP8L` dimensions in `_clean_webp`, verify they match `VP8X` and `_size_ok()`, and reject duplicate `VP8X` chunks. In `_decode`, use an explicit `mismatch = False` flag set inside `prepared()`.

11. **Low — [theme_core.py:535-551](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L535-L551) — `theme_manager_toggle` does not verify plugin directory ownership/writability**
    - **Failure scenario:** `theme_manager_toggle()` checks `os.lstat(script)` for ownership and non-group/other-writability, but does not verify the containing `folder` itself (`os.stat(_real(folder))`). If the directory were group- or world-writable, `theme-toggle` could be replaced between `theme_manager_toggle()` and `Popen()`.
    - **Suggested fix:** Check that `_real(folder)` is owned by `os.getuid()` and has no `S_IWGRP | S_IWOTH` bits set.

12. **Low — [theme_core.py:435-439](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/theme_core.py#L435-L439) — `current_slug()` fallback returns `"unknown"` instead of `""` when `theme.name` is missing**
    - **Failure scenario:** Verified in `/usr/bin/omarchy-theme-current:10-12`: when `~/.local/state/omarchy/current/theme.name` does not exist, `omarchy theme current` prints `Unknown` and exits 0. `slug_of("Unknown")` produces `"unknown"`, which passes `valid_slug("unknown")`, so `current_slug()` returns `"unknown"` instead of `""` (falsely marking a theme named `unknown` as current if one exists).
    - **Suggested fix:** Call `["omarchy-theme-current"]` directly and ignore `"unknown"` (or require `slug in theme_folders()`).

13. **Low — [tests/test_theme_core.py:470-471](file:///mnt/Data/Projects/omarchy-settings-manager-wt/a-theme/tests/test_theme_core.py#L470-L471) — Unhandled reaper-thread exception in unit tests and missing regression tests**
